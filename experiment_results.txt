CS314 PS9 - Binary Search Tree Experiment Results
=================================================

These results were produced by Experiments.java (run: `java Experiments`).
Each configuration is averaged over 10 trials. Times are in seconds.
Exact numbers vary run to run with machine load; the trends are what matter.

Notes:
- Size is very close to N; it dips slightly below N at large N because the
  random number generator occasionally produces duplicate values, which are

- Total insertion work is about O(N log N), so each doubling of N roughly
  doubles the time (a little more because of the log factor).


2. Minimum possible tree height for N unique values
----------------------------------------------------
The minimum possible height occurs when the tree is as balanced (complete) as
possible, giving height = floor(log2(N)). Values are shown in the "minHeight"
column above (9, 10, 11, ... 19). The BST's observed random heights are about
2x to 2.5x this minimum.

Comparison to BinarySearchTree (random input):
- TreeSet (a red-black balanced tree) and our BST perform almost identically
  on random data. Both are O(N log N) overall and the measured times track
  each other closely across every N.
- This makes sense: with random input the unbalanced BST stays close to log N
  height on average, so it is competitive with the guaranteed-balanced TreeSet.


4. BinarySearchTree - sorted (ascending) integers
--------------------------------------------------
           N         avgTime(s)     height         size
        1000           0.001223        999         1000
        2000           0.003681       1999         2000
        4000           0.014557       3999         4000
        8000           0.057906       7999         8000
       16000           0.232458      15999        16000
       32000           0.927059      31999        32000
       64000           4.069181      63999        64000

Notes:
- Height and size are known without calling the methods: inserting already
  sorted values builds a completely degenerate tree (a linked list leaning
  right), so height = N - 1 and size = N.
- Each insertion walks the full chain, so building the tree is O(N^2). The
  times confirm this: every doubling of N multiplies the time by about 4x.


5. Predicted sorted BinarySearchTree times (O(N^2) scaling)
-----------------------------------------------------------
Using the 64,000 measurement as the baseline and the 4x-per-doubling rule:
      128000          ~16.3 s (predicted)
      256000          ~65.1 s (predicted)
      512000         ~260.4 s (predicted)

(These are predictions, not measured. They were not run directly because the
quadratic blow-up makes them very slow. Note: the recursive add method would
also overflow the call stack on this many sorted values, which is a second
reason degenerate trees are a problem; the driver uses iterativeAdd here.)


6. TreeSet - sorted (ascending) integers
----------------------------------------
           N         avgTime(s)
        1000           0.000057
        2000           0.000119
        4000           0.000293
        8000           0.000566
       16000           0.001196
       32000           0.002443
       64000           0.005465

Comparison and cause of the difference:
- TreeSet is dramatically faster than our BinarySearchTree on sorted input.
  At N = 64,000 TreeSet takes about 0.005 s while the BST takes about 4 s,
  a difference of roughly three orders of magnitude.
- TreeSet stays O(N log N) because it is self-balancing (red-black tree): it
  rotates nodes during insertion so the height stays ~log N no matter what
  order the data arrives in.
- Our BinarySearchTree does no balancing, so sorted input produces a
  degenerate height-(N-1) chain and insertion degrades to O(N^2). The cause of
  the difference is entirely the balancing: with sorted data the unbalanced
  tree is worst case while the balanced tree is still best case.
